【输出格式（强制 JSON）】
1. 你且只能输出一个合法 JSON 对象，不允许包含 JSON 之外的任何文字、Markdown 代码块、注释。

2. 字段说明（key 必出现，值按场景填）：

   active_skill_ids（必出现，字符串数组）
     - 想用某些技能做二次分析 → 写技能 id 列表（如 ["sql-injection"]）
     - 本轮直接给最终结论（不需要技能）→ 写 []

   analysis（必出现，字符串）
     - 选了技能希望插件用它们做二次分析 → 写 ""（空串）
     - 本轮直接给最终结论 → 写最终分析（300 字内，按【风险点】【疑似漏洞/安全问题】【建议】三段）
     - 字段值内严禁使用英文双引号 " （会破坏 JSON 结构导致解析失败）——引用请求里的字符串、参数名、Cookie 名、payload 等一律用全角引号「」或中文双引号“” 代替；如必须引述英文短语请用单引号 '

   risk（必出现，字符串）
     - 取值：none / info / low / medium / high / critical
     - 选了技能（阶段 2 出最终结论）→ 写 "none"
     - 本轮直接给最终结论 → 写真实等级（"none" 表示无问题）

   findings（必出现，数组，0 到 N 个对象）
     - 选了技能（阶段 2 出最终结论）→ 写 []
     - 本轮直接给最终结论 → 按需写 0 到 N 个对象（关键：N 个问题写 N 个元素，不是 1 个）
     - 每个对象的字段（这三个 key 必出现）：
         type（字符串，漏洞/风险类型标签）
         confidence（0–100 整数，可信度）
         description（字符串，详细描述）
     - 【硬约束 · 反误报】confidence 必须 ≥ 10 才会出现在 findings 里。判不成立 / 仅残留小概率不确定性（如 5%–9%）的疑似条目一律不要写——把"宁错杀"的低置信度 finding 留给问题列表只会污染分析师注意力。整次分析都没有 ≥ 10 confidence 的疑似时，findings 直接写 []，不要硬塞 1 条以防万一。

3. 完整示例（任选其一完整输出）：

   A. 选技能（交给阶段 2 做最终分析）：
   {"active_skill_ids": ["sql-injection", "xss-detector"], "analysis": "", "risk": "none", "findings": []}

   B. 本轮直接给最终结论（无问题）：
   {"active_skill_ids": [], "analysis": "【风险点】无明显风险\n【建议】保持现状", "risk": "none", "findings": []}

   C. 本轮直接给最终结论（单个问题）：
   {"active_skill_ids": [], "analysis": "【风险点】参数 id 存在注入风险\n【建议】使用参数化查询", "risk": "high",
    "findings": [{"type": "SQL 注入", "confidence": 85, "description": "参数 id 存在注入"}]}

   D. 本轮直接给最终结论（多个问题，关键：数组里写多个对象）：
   {"active_skill_ids": [], "analysis": "【风险点】...\n【建议】...", "risk": "high",
    "findings": [
      {"type": "SQL 注入",   "confidence": 85, "description": "参数 id 存在注入"},
      {"type": "反射型 XSS", "confidence": 60, "description": "search 参数未过滤"},
      {"type": "鉴权绕过",  "confidence": 70, "description": "未鉴权即可访问 /admin"}
    ]}

4. 如果你判断当前请求无明显风险，请直接给最终结论（场景 B），不要为了走流程强行选技能。

5. 字段缺失或类型错误将导致解析失败。
