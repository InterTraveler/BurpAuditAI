[Output format (strict JSON)]
1. Output one and only one valid JSON object. Do not include any text, Markdown code fences, or comments outside the JSON.

2. Field reference (every key is mandatory; fill the values per the scenario):

   active_skill_ids (mandatory, array of strings)
     - You want some skills to run a second-pass analysis -> write the skill ids (e.g. ["sql-injection"])
     - You are giving the final conclusion directly this turn (no skill needed) -> write []

   analysis (mandatory, string)
     - Skills selected for a second pass -> write "" (empty string)
     - Final conclusion this turn -> write the analysis (English, within 300 words; three parts: [Risk points], [Suspected vulnerability / security issue], [Recommendation])

   risk (mandatory, string)
     - Allowed values: none / info / low / medium / high / critical
     - Skills selected (phase 2 produces the final conclusion) -> write "none"
     - Final conclusion this turn -> write the real level ("none" means no issue)

   findings (mandatory, array of 0 to N objects)
     - Skills selected (phase 2 produces the final conclusion) -> write []
     - Final conclusion this turn -> write 0 to N objects as needed (key: N issues = N elements, not 1)
     - Each object has these three mandatory keys:
         type (string, vulnerability / risk type label)
         confidence (integer 0-100, confidence)
         description (string, detailed description)
     - [Hard rule, anti-false-positive] Only include a finding when confidence >= 10. Suspected entries that are not actually established -- including lingering low-probability uncertainty (e.g. 5%-9%) -- must be omitted from the findings array. Lining the issue list with low-confidence "just-in-case" entries drowns out real signals. If nothing in this request reaches confidence 10, write findings = []; do not insert a defensive entry.

3. Complete examples (output exactly one of the shapes):

   A. Use skills (let phase 2 produce the final analysis):
   {"active_skill_ids": ["sql-injection", "xss-detector"], "analysis": "", "risk": "none", "findings": []}

   B. Final conclusion this turn (no issues):
   {"active_skill_ids": [], "analysis": "[Risk points] No obvious risk\n[Recommendation] Keep current state", "risk": "none", "findings": []}

   C. Final conclusion this turn (one issue):
   {"active_skill_ids": [], "analysis": "[Risk points] The id parameter is vulnerable to injection\n[Recommendation] Use parameterized queries", "risk": "high",
    "findings": [{"type": "SQL injection", "confidence": 85, "description": "The id parameter is injectable"}]}

   D. Final conclusion this turn (multiple issues, key: one element per issue):
   {"active_skill_ids": [], "analysis": "[Risk points] ...\n[Recommendation] ...", "risk": "high",
    "findings": [
      {"type": "SQL injection",            "confidence": 85, "description": "The id parameter is injectable"},
      {"type": "Reflected XSS",            "confidence": 60, "description": "The search parameter is not encoded"},
      {"type": "Broken access control",    "confidence": 70, "description": "/admin reachable without authentication"}
    ]}

4. If you judge that the current request has no obvious risk, give the final conclusion directly (scenario B). Do not force skill selection just to run through the flow.

5. Missing or mistyped fields will make parsing fail.
