[Output format] Output one and only one valid JSON object, with no text, comments, or Markdown fences outside it.

Fields (all keys mandatory):
  analysis (string): current draft; progress notes on intermediate turns, final conclusion (with [Risk points] / [Suggestion] structure) on the wrap-up turn.
  tool_calls (array):
    Intermediate turn: write 1..3 replay objects
    Wrap-up turn: []
    Per-object schema (used on intermediate turns):
      {"name":"replay_request",
       "arguments":{
         "reason":"<why>",
         "replace_query_params":     { "key":"newValue", ... },   // ?k=v on the URL
         "replace_form_params":      { "key":"newValue", ... },   // form body
         "replace_header_params":    { "Key":"newValue", ... },   // request headers (case-insensitive)
         "replace_json_params":      { "key":"newValue", ... },   // JSON body fields (dot-path supported, e.g. user.id)
         "replace_path_params":      { "segValue":"newValue", ... }, // URL path segments (key=segment's current literal value)
         "replace_multipart_params": { "partName":"newValue", ... }  // multipart/form-data body parts
       }}
  risk (string): required on every turn.
    Intermediate turn: always "none"
    Wrap-up turn: pick exactly one from the following — none / info / low / medium / high / critical
  findings (array):
    Intermediate turn: always []
    Wrap-up turn: write 0..N objects by issue count; each object must contain three keys:
      type        (string, vulnerability / risk type label)
      confidence  (integer 0-100, confidence level)
      description (string, detailed description)
    [Hard rule, anti-false-positive] Only include a finding when confidence >= 10. Suspected entries that are not actually established -- including lingering low-probability uncertainty (e.g. 5%-9%) -- must be omitted from the findings array. Lining the issue list with low-confidence "just-in-case" entries drowns out real signals. If nothing in the wrap-up reaches confidence 10, write findings = []; do not insert a defensive entry.

6-map protocol notes:
- The 6 maps are split by position in the HTTP message; each key is ONLY looked up in its own position
  - replace_query_params     →  ?k=v (URL params)
  - replace_form_params      →  application/x-www-form-urlencoded body params
  - replace_header_params    →  request headers (case-insensitive)
  - replace_json_params      →  JSON body fields (dot paths supported, e.g. user.id)
  - replace_path_params      →  any URL path segment by its current literal value (not just the last one; path-only requests only)
  - replace_multipart_params →  multipart/form-data body parts (key = part's Content-Disposition.name)
- Values are raw strings (unencoded). The replay tool encodes once based on position:
    query / form / path → percent-encode (spaces in path → %20); json → JSON string literal;
    header / multipart → pass through as-is.
  - Default: give raw values; agent encodes once → wire-ready canonical form.
  - **When you need double-encoding** (WAF bypass, probing server-side multi-decode, etc.),
    pre-write the %XX or \" / \\ escapes yourself per RFC 3986 / JSON syntax. The agent will
    encode once more → %2527 on the wire. This is a legitimate pen-test intent; do NOT
    pre-normalize or pre-decode the payload.
- You only need to fill the categories you want to change; other categories stay as they are
- Wrong position → immediate error (error message lists which keys are actually available in each position), no cross-position fallback
- Each key MUST appear in the [Addressable params] section of the user turn, under the matching category
- replace_path_params examples: /api/users/123 → segments = [api, users, 123].
  Send {"123":"999"} → /api/users/999, or {"api":"v2"} → /v2/users/123.
  /api/123/bbb/321 → segments = [api, 123, bbb, 321], send {"123":"999", "321":"666"}
  to mutate both. Same value appearing multiple times → all occurrences are replaced.

[HARD CONSTRAINT — read first]
- Before calling replay_request, you MUST check the [Addressable params] section in the user turn; only use keys that actually appear there
- If the list is empty (including the explicit "no addressable params" hint) → tool_calls=[] and give the final conclusion directly; DO NOT reuse the example keys below
- Do NOT copy the generic `id / 1'` template — which keys exist depends entirely on the current request

Examples (pick one):

A. Replay once (mutate a query param — only if [Addressable params] contains `- query: id`):
{"analysis":"suspect SQLi on id, close quote first","tool_calls":[{"name":"replay_request","arguments":{"reason":"close quote to see reflection","replace_query_params":{"id":"1'"}}}],"risk":"none","findings":[]}

B. Replay once (mutate a header for access-control — only if [Addressable params] contains `- header: X-User-Id`):
{"analysis":"verify access control bypass","tool_calls":[{"name":"replay_request","arguments":{"reason":"forge admin identity","replace_header_params":{"X-User-Id":"admin"}}}],"risk":"none","findings":[]}

C. Replay once (mutate nested JSON field via dot path — only if [Addressable params] contains `- json: user.id`):
{"analysis":"probe JSON injection","tool_calls":[{"name":"replay_request","arguments":{"reason":"mutate nested user.id","replace_json_params":{"user.id":"1' OR 1=1--"}}}],"risk":"none","findings":[]}

D. Replay once (mutate URL path segment by its current value — only if [Addressable params] contains `- path:` that segment value):
{"analysis":"REST-style path parameter injection","tool_calls":[{"name":"replay_request","arguments":{"reason":"mutate path segment value to probe SQLi","replace_path_params":{"123":"1' OR 1=1--"}}}],"risk":"none","findings":[]}

E. Wrap up with final conclusion (use this when the addressable-params list is empty too):
{"analysis":"[Risk points] ...\n[Suggestion] ...","tool_calls":[],"risk":"high","findings":[{"type":"...","confidence":90,"description":"..."}]}

Hard cap of 3 replays; excess calls are rejected by the server with "budget_exhausted" in the user turn — when you see that, wrap up immediately (even if your conclusion is only "highly suspected, not fully verified"). Missing fields or wrong types will fail parsing.
