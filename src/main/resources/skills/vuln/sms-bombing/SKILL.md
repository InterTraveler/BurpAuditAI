本技能专注于"短信 / 邮件轰炸"和"验证码逻辑缺陷"的发现。在 SRC 实战里，"发一条验证码就能让用户持续收到短信"是高赏金的"骚扰型"漏洞，单独报可拿 100-500。常见相关：图形验证码绕过、验证码可复用、验证码数量过大可暴力、限速只跟 IP 不跟业务 ID、上下行不一致导致轰炸自己等。在你识别到疑似发送入口时，按以下流程处理：
1. 识别"发送入口"与触发链路：
   - URL 含 sendCode / sendSms / sendEmail / sendOtp / getCode / sendCodeTo / sendCaptcha / sendCaptchaByMobile / sendEmailCode；
   - 业务关键词：注册 / 登录 / 改密 / 重置 / 绑定手机 / 验证手机 / 实名认证 / 绑定邮箱 / 提现 / 转账 / 评论通知 / 关注通知 / 营销订阅；
   - 触发动作：body 里有 mobile / phone / email / account，响应 200 / {"success":true} / {"code":0} 即视为已发送。
2. 探测"限速维度"（按权重）：
   - 维度 1（业务唯一标识）：同一个 mobile / email 在 X 分钟内只允许 1 次 → 看重放第 2 次是否仍返回 200；
   - 维度 2（IP）：同一 IP 在 X 秒内只允许 N 次 → 换 IP 看（X-Forwarded-For / X-Real-IP 头）；
   - 维度 3（图形 / 滑块验证码）：看请求是否需要 captchaId / captchaCode / slideToken → 没有 = 一开始就该高危；
   - 维度 4（session）：同 JSESSIONID / PHPSESSID 是否复用计数；
   - 维度 5（图形验证码绕过）：图形验证码跟业务 ID 不绑定 → 同一 captchaCode 多次复用；
   - 维度 6（手机号维度）：用中国手机号段连发，看是否每个号都能收到；
3. 探测"验证码自身逻辑缺陷"：
   - 验证码长度：4 位 = 10000 种可暴力（必须短信轰炸绕过限速才能试）；6 位 = 10^6 不现实；
   - 验证码有效期：无 / 30 分钟 / 1 小时（合理为 5-10 分钟）；
   - 验证码可重用：一次对错后再次重发，原验证码是否仍可用；
   - 验证码数量过大（位数 + 有效期组合）：5 位 + 5 分钟 = 可破；
   - 验证码响应体泄漏：响应体里直接返回验证码 / 提示"验证码已发送到 xxx@yeah.net" = 凭证泄露；
   - 验证码与目的不绑：注册验证码拿去重置密码也能用（用 forgot-password 技能）；
   - 验证码同号跨业务：A 业务拿的验证码用在 B 业务 = 逻辑缺陷；
   - 验证码与用户不绑：任意手机号能拿任意用户的验证码 → 接管；
   - 短信上行验证 (Upstream SMS)：客户端发特定号码上行一条短信完成验证 → 业务流程逻辑问题；
   - 邮箱链接泄漏 token：邮件正文 link 里有 token，链接 host 是否白名单、token 是否一次性。
4. 评估危害等级：
   - critical：验证码与用户不绑 / 同验证码跨业务通用 / 验证码在响应体里直接返回 / 验证码数量过短（4 位）+有效期过长（10 分钟+）+ 限速失效 = 任意接管任意用户；
   - high：纯短信轰炸（无任何限速） + 业务上是高频场景（注册 / 重置）；
   - medium：限速存在但绕过得很快（换 IP / 换 captchaCode 复用）；
   - low：限速存在但有触发条件（需特定 IP / 特定 captchaCode 才能绕过）。
5. 给出修复建议：限速维度必须跟"业务唯一标识"绑定（mobile + IP + 设备指纹）；图形验证码必须跟 session 绑定 + 一次性；验证码有效期 5 分钟内；一次性且用后即失效；短信发送走第三方平台但服务端记录发送记录 + 触发熔断（如 1 分钟内同号超过 3 次直接冻结 24 小时）；验证码不返回到响应体；验证码与目的强绑（注册码不能用在重置）；不要在内部短信网关加白名单 IP（这是反模式）。
所有由本技能产出的 finding 必须设置 type=sms-bombing。多个技能可能同时被激活，本技能不负责密码重置 token 可预测（那是 forgot-password）/ 鉴权流程缺陷（绕过登录拿到账号，那是 auth-bypass）/ OAuth 接管（那是 oauth）/ 验证码作为暴力工具本身（拿到验证码后暴力登录接口，那是 brute-force 已被本插件下架，建议用 hydra / ffuf 工具验证）。
【重放建议】短信轰炸重放有 3 次硬上限（orchestrator 管控），按：
- 第 1 次：用自己测试号连发 3 次同请求，看是否都 200 + 实际收到 3 条短信（确认无业务 ID 限速）；
- 第 2 次：加 X-Forwarded-For: 1.2.3.4 看是否仍 200（IP 维度绕过）；
- 第 3 次（精调）：换 mobile 后缀（自己测试号轮换最后 4 位），看是否都能成功（确认业务 ID 限速是否生效）。
重放成本极高（每条短信真的发出去会扣费），重放前必须先判断"是否值得发"。推荐前两次先用目标公司自己的邮箱或合作伙伴允许的沙箱号验证，第三次再用真实测试号。本技能是"分析建议"而非"硬性规则"，最终判断权交给模型。
- 【反误报】给 finding 设 confidence 时，只在能解释清楚"为什么 ≥ 60" 时给 ≥60；判不成立 / 仅残留小概率不确定性（如 5%–20%）的疑似不要写进 findings——本插件解析阶段会再过一道阈值（约 30）兜底，但 prompt 层的克制才是从源头减少问题列表噪声 finding 的关键。
